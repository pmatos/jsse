# Library Tests: TypeScript unit tests

Split from [library-tests-typescript.md](library-tests-typescript.md) to keep each file under the 20,000-byte budget. The tsserver halves are in [library-tests-typescript-tsserver.md](library-tests-typescript-tsserver.md).

- **TypeScript top-level unit tests**: `TS_SRC_DIR=<built TypeScript v6.0.3 checkout> uv run python scripts/run-ts-unittests-oracle.py [--jobs N] [--no-light] [--test-timeout MS] [--jsse-arg ARG] [group-glob ...]` runs the 26 `src/testRunner/unittests/*.ts` files (asserts, base64, builder, canWatch, comments, compilerCore, customTransforms, incrementalParser, jsDocParsing, moduleResolution, printer, programApi, publicApi, reuseProgramStructure, semver, transform, regExpScannerRecovery, ...; table in `scripts/ts_unittests_groups.py`, 2334 tests) through mocha and `built/local/run.js` on Node and `jsse --node` and compares the per-test pass/fail sets (JSON reporter), not totals. Node must pass the pinned count; a test failing on jsse must be listed in `ts-suite/unittests-core-known-failures.txt` (empty: all 2334 pass in light and full mode), and a listed test that passes fails the run (ratchet); a `describe` the table misses fails the run. Four processes per engine (`batch`), about 6 minutes at 4 jobs because each jsse process spends 80 s loading the 13 MB runner bundle; `--test-timeout` defaults to 600000 ms because the first `Program` of a suite parses `lib.d.ts` (25 to 75 s on jsse, 0.3 s on Node), which exceeds hereby's 40 s. Skips without `TS_SRC_DIR`. Guards: `tests/node_ts_unittests.rs`, `scripts/test_run_ts_unittests_oracle.py`; design: `docs/adr/2026-10-28-1600-node-host-unittests-core.md`.
- **TypeScript services unit tests** (#1261): the same script and table cover `src/testRunner/unittests/services/*.ts` and `services/extract/*.ts` as 16 `services-*` groups (1531 tests: convertToAsyncFunction 264, extractConstants 92, extractFunctions 122, extractRanges 50, extract Symbol Walker 1, organizeImports 91, textChanges 84, languageService 6, cancellableLanguageServiceOperations 5, documentRegistry 4, hostNewLineSupport 3, utilities 1, patternMatcher 75, preProcessFile 41, colorization 38, transpile 654), run as `... run-ts-unittests-oracle.py 'services-*'` in four batches (about 10 minutes at 4 jobs, light mode); a bare run executes all 93 groups (4625 tests with the evaluation groups of #1262 and the tsbuild groups of #1264, 15 processes per engine) in about twenty-five minutes, and `check_groups` also walks `unittests/services/` recursively for a `describe` no group selects (a missing directory is a problem). All 1531 pass on both engines in light and full mode (`--no-light`), so the known-failure list stays empty. Guard: the `small_services_groups_*` case of `tests/node_ts_unittests.rs`; design: `docs/adr/2026-10-28-1700-node-host-unittests-services.md`. The other subdirectories (`tsserver`, ...) belong to their own tickets.
- **TypeScript evaluation unit tests** (#1262): the same script and table cover `src/testRunner/unittests/evaluation/*.ts` as 20 `evaluation-*` groups (350 tests, the `evaluation` suite of `ts-suite/oracle.json`: esDecorators 162, awaitUsing 44, using 41, autoAccessors 12, esDecoratorsMetadata 12, forAwaitOf 11, optionalCall 13, ...), run as `... run-ts-unittests-oracle.py 'evaluation-*'` (three processes per engine, about two minutes at 3 jobs). Each test compiles a snippet with `evaluator.evaluateTypeScript` and runs the emitted code through `new Function`. All 350 pass on both engines, so the known-failure list stays empty; the one difference found (V8's `undefined is not iterable (cannot read property Symbol(Symbol.iterator))` TypeError text) was fixed in `Interpreter::nullish_computed_read_message` (guard: `tests/nullish-iterator-read-message.js`). `check_groups` also walks `unittests/evaluation/`. Guard: the `evaluation_groups_*` case of `tests/node_ts_unittests.rs`; design: `docs/adr/2026-10-28-1800-node-host-unittests-evaluation.md`.
- **TypeScript tsbuild unit tests** (#1264): 31 `tsbuild-*` groups (rows in `scripts/ts_unittests_tsbuild_groups.py`, 410 tests: sample1, noEmit, noEmitOnError, commandLine, resolveJsonModule, noCheck, outFile, roots, declarationEmit, ...), run as `... run-ts-unittests-oracle.py 'tsbuild-*'` in four batches (about 5 minutes at 4 jobs), all 410 pass on both engines in light and full mode, so the known-failure list stays empty; `check_groups` also walks `unittests/tsbuild/` (`tsbuildWatch` is covered by the #1265 oracle). Guard: the `small_tsbuild_groups_*` case of `tests/node_ts_unittests.rs`; design: `docs/adr/2026-10-28-1800-node-host-unittests-tsbuild.md`.
- **TypeScript unit tests: config, sys, debugDeprecation** (#1260): `TS_SRC_DIR=<built TypeScript v6.0.3 checkout> uv run python scripts/run-ts-unittests-config-sys-oracle.py [--jobs N (at most 4)] [--verbose] [--record] [group ...]` runs mocha's CLI on `built/local/run.js` (the `unittest` runner, light mode off) once per group of `scripts/ts_unittest_groups.py` on Node and `jsse --node` with the json reporter and compares the outcome of every test title (multiset, duplicate titles included). The groups are `unittests:: config::` (commandLineParsing, configurationExtension, convertCompilerOptionsFromJson, convertTypeAcquisitionFromJson, initTSConfig, matchFiles, showConfig, tsconfigParsing and its watch options: 519 tests), `unittests:: sys:: symlinkWatching` (16 tests, the real `ts.sys` file watchers plus the virtual file system, with `fs.watch` and symlinks) and `unittests:: debugDeprecation` (6); the counts equal the per-suite counts pinned in `ts-suite/oracle.json`. `unittests/helpers/*.ts` registers no test of its own: it holds the builders (virtual file system with watch, tsc, tscWatch, tsserver, solution builder) the tsc, tsbuild, tscWatch and tsserver suites run, so those groups cover it. `ts-suite/unittests-config-sys.json` holds the expected Node counts per group and `known_failures` (test title -> issue; empty: all 541 tests pass on both engines). A test that passes on Node and fails on jsse and is not listed, a listed test that now passes, a Node failure or a changed count exits 1 (skips without `TS_SRC_DIR` unless `--require`; never writes into the checkout). `--record` rewrites the file. A jsse run costs about 30 s per group, nearly all of it loading the 13 MB runner bundle. Guards: `tests/node_ts_unittests_config_sys.rs`, `scripts/test_run_ts_unittests_config_sys_oracle.py`.
- **TypeScript unit tests: `tsc` CLI scenarios** (#1263): `TS_SRC_DIR=<built TypeScript v6.0.3 checkout> uv run python scripts/run-ts-unittests-tsc-oracle.py [--jobs N (at most 4)] [--verbose] [--record] [group ...]` is the #1260 oracle (`scripts/run-ts-unittests-config-sys-oracle.py`, loaded by the wrapper, same options and comparison) over the 17 groups of `scripts/ts_unittest_tsc_groups.py`, one per file of `src/testRunner/unittests/tsc` (`unittests:: tsc:: ...`: cancellationToken, commandLine, composite, declarationEmit, extends, forceConsistentCasingInFileNames, ignoreConfig, incremental, libraryResolution, listFilesOnly, moduleResolution, noCheck, noEmit, noEmitOnError, projectReferences, projectReferencesConfig, redirect: 297 tests, equal to the `tsc` suite pinned in `ts-suite/oracle.json`; `tscWatch`, `tsbuild` and `tsbuildWatch` are other tickets). The baseline is `ts-suite/unittests-tsc.json` (counts per group and `known_failures`, test title -> issue). Guards: `tests/node_ts_unittests_tsc.rs`, `scripts/test_run_ts_unittests_tsc_oracle.py`.
- **TypeScript unit tests: `tscWatch` and `tsbuildWatch`** (#1265): `TS_SRC_DIR=<built TypeScript v6.0.3 checkout> uv run python scripts/run-ts-unittests-watch-oracle.py [--jobs N (at most 4)] [--verbose] [--record] [group-glob ...]` is the #1260 oracle (`scripts/run-ts-unittests-config-sys-oracle.py`, same options and per-title multiset comparison) over the 33 groups of `scripts/ts_unittest_watch_groups.py`, one per file of `src/testRunner/unittests/tscWatch` (20 `tscWatch-*` groups, 375 tests) and `unittests/tsbuildWatch` (13 `tsbuildWatch-*` groups, 82 tests); the counts equal the `tscWatch` and `tsbuildWatch` suites pinned in `ts-suite/oracle.json` (the pin files the one top-level `it` of `tsbuildWatch/publicApi.ts` under "other", so it holds 81). These suites run on the fake watch host of `unittests/helpers/virtualFileSystemWithWatch.ts` (virtual timers and file events, no real `fs.watch`), so they are CPU-bound: one jsse process per group (30 to 75 s, nearly all of it loading the 13 MB runner bundle), about 6 minutes for the whole set at 4 jobs (`'tscWatch-*'` and `'tsbuildWatch-*'` run each half). All 457 pass on both engines (full mode), so `ts-suite/unittests-watch.json` (counts per group, `known_failures`: test title -> issue) lists no known failure. Guards: `tests/node_ts_unittests_watch.rs`, `scripts/test_run_ts_unittests_watch_oracle.py`.
