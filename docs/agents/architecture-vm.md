# VM, functions, and environments

- The interpreter is a single-pass tree-walker over the AST. A bytecode compiler/VM in `bytecode/` is the default execution mode (`bytecode_enabled` defaults on; `--no-bytecode` opts out); in Function goal a construct the compiler cannot lower falls back to the tree-walker per *node* (`Op::EvalAst`/`Op::ExecAst`, ADR-2026-10-12-2214), and only `CompileError::Ineligible` constructs (direct `eval`, `with`, `super`, `new.target`, compiler resource limits, a body that is nothing but hand-offs) keep a whole function body on the tree-walker; a `yield`/`await` the scan meets can only sit inside a nested arrow, which owns it, so it is not one of them (#907). The Script goal falls back per node too, with valued completions (`EXEC_SET_COMPLETION`, ADR-2026-10-13-1210): it stays whole-body only for direct `eval`, `with`, `import()`/`import.meta` and a script that is nothing but hand-offs. Native lowerings include `switch`, `throw`, `typeof`, member `++`/`--`, `instanceof`, `in`, private-name accesses (`GetPrivate`/`SetPrivate`/`UpdatePrivate`/`LoadMethodPrivate`/`PrivateIn`; each frame resolves a chunk private-name index to its per-class-evaluation `PrivateId` once), BigInt literals and function-top-level `let`/`const`; block, `for (let ...)` and `switch` scopes run in VM-managed block environments (`PushEnv`/`PopEnv`/`CopyIterEnv`, ADR-2026-10-13-0632); array literals (`NewArray`/`NewArrayConst`/`ArrayAppend`), statically keyed object literals (`NewObject`/`ObjectAppend`), regular expression literals (`NewRegExp`) and function/arrow closures with NamedEvaluation (`MakeClosure`) are native too (ADR-2026-10-13-0755); array literals with spread or non-constant elisions, object literals with computed keys or spread, class expressions and destructuring declarations other than plain-name `let`/`const` object patterns run as tree-walker nodes (see the `FALLBACK` counters). A `let`/`const` object pattern whose properties are all `name` or `key: name` is native (#1101, `compiler/lexical.rs`): each non-final property is `DupN 1; GetProp; InitLexical`, the last one `GetProp; InitLexical` on the source itself; a nullish source fails at the first read, before anything observable, so there is no separate RequireObjectCoercible op. Defaults, rest, computed or non-UTF-16 keys, nested patterns and the empty pattern stay on the tree-walker. Calls and `new` with spread arguments are native (#1100, `compiler/calls.rs`, `vm/spread.rs`): a spread pushes the iterable's elements on the operand stack as arguments, rooted one by one like any operand, and a Number slot above them carries the running argument count (`ArgSpreadFirst`/`ArgSpread`/`ArgPush`, then `CallSpread`/`ConstructSpread`; a lone spread skips the slot with `CallSpreadSole`/`ConstructSpreadSole`). Because that count is dynamic, the compiler's static stack model counts only the arguments before the first spread plus the count slot, and nothing may address an operand from below across one; handlers still cut the stack back to their static height. `super(...)`, optional calls, direct `eval` and a strict `return f(...)` (its `TailCall`) stay on the tree-walker. `try`/`catch`/`finally`, `for-in` and `for-of` are native too (ADR-2026-10-13-1019): a per-chunk handler table resumes a `Throw`, a `finally` block is entered once with a completion record `[value, kind]` that `EndFinally` re-dispatches, and a for-of's iterator is an operand-stack slot closed by `IterClose`/`IterCloseThrow`; a tree-walker hand-off inside one of those regions that would complete with a `return`/`break`/`continue` out of it keeps the whole construct on the tree-walker (`completion leaves a cleanup region`). At Script top level they remain tree-walker units. Property-access MOP operations ([[Get]], [[Set]], [[DefineOwnProperty]], [[Delete]], [[HasProperty]], proxy traps, array/typed-array exotic) are consolidated in `property.rs`.
- Per-literal call-frame facts live in `LiteralFrame` (`literal_frame.rs`, #1062): created with a literal's `FunctionLiteralInfo`, shared by `Rc` with every closure (`JsFunction::User.frame`), and holding the interned simple-parameter atoms (plus whether they are fresh, i.e. distinct and not `arguments`, so binding can `push_unique`) and the `BodyStoreHandle` of the literal's IC store. `IcStore::enter_body_cached` revalidates the handle by slot generation and Body identity; functions built without a literal (`Function` constructor and siblings) own a fresh frame.
- `Environment.bindings` is a `BindingMap` (`binding_map.rs`) of interned `Atom`s (`atom.rs`): linear scan up to 16 entries, identity-hashed atom index above that, `this` held in `Environment.this_binding`, and the `arguments` binding declared only when the body can observe it. The interner is the only place identifier text is hashed (randomised, see `docs/specs/2026-07-25-environment-binding-hashing-design.md`). Compiled function bodies use `LoadLocal`/`StoreLocal`/`UpdateLocal` with slot hints verified by atom identity (ADR-2026-10-12-0900). The frame layout is `arguments`, the simple parameters, the var-prologue names, the top-level function-declaration names and the top-level `let`/`const`/class names, in the order declaration instantiation creates them (`compiler::instantiated_names`, only when every `var` name is in the prologue and the parameters are simple); `InitLexical` takes the same slot at function top level (#1022). A function whose parameters are plain names with defaults or a rest element (`LiteralFrame::named_param_plan`, bound by `bind_named_parameters`) runs its body in the parameter environment, with the same frame layout as a simple-parameter function, when `LiteralFrame::shares_param_env` proves the separate body environment unobservable (no closure or direct `eval` in the defaults, no direct `eval`, function declaration or `arguments` declaration in the body); otherwise it gets a pooled body environment (#1024). A free name that is not a frame local keeps a `ScopeHint` in its `GlobalHint`: the hops from the nearest function scope plus the binding slot (or a global-object marker with the key-set stamp of the global environment's indexed `BindingMap`), re-verified on every use by `global_access::walk_scope_chain_hinted` (each skipped scope must not bind the name, one name-filter probe each) and retrained by a full walk when it fails. A free name that resolves to an own data property of the global object takes the Global Data Fast Path (ADR-2026-10-12-1500): `PropertyMap`'s spilled storage is a dense entry list plus a key→slot index so each bytecode name site can remember a verified slot (`Chunk.global_hints`). In a Script chunk, a bare-name site inside a block scope whose name no open block scope declares gets its own name-pool entry (`Compiler::name_site`) whose `GlobalHint::starts_at_frame` makes the VM resolve it from the frame (global) environment, skipping the per-block-scope hint verification; `store_resolved_name` also writes an initialised global `let` binding directly (it is never mirrored on the global object).
- Sync generators whose body the compiler can host run as suspending bytecode chunks (`IteratorState::BytecodeGenerator`, ADR-2026-10-17-0640): `compile_generator_body` is the Function goal with `Op::Yield`, which returns `Completion::Yield` from `run_chunk_inner` after saving the position and block environments into the generator's `GeneratorFrame` (the operand and reference stacks are the frame's own vectors); `run_generator_chunk` resumes it, and `bytecode_generator_resume` is the single `next`/`return`/`throw` implementation. `return(v)` resumes at the stub after the yield, the exit a `return` statement would emit there; `throw(e)` resumes through the ordinary handler table. A body containing `yield*`, `using`, or a `yield` inside a node the compiler hands to the tree-walker (`EvalAst`/`ExecAst`, a head-binding pattern) is `Ineligible` and keeps the state machine, as does every generator under `--no-bytecode`. Keep `JsObjectData`-visible changes to the suspended frame traced in `collect_iterator_state_roots`.
- Async functions whose body the compiler can host run as suspending chunks too (`eval/async_chunk.rs`, ADR-2026-10-19-2030): `await` is `Op::Yield` with a zero skip offset (no return stub; a driver tells it from a `yield` by that operand), `compile_async_body` is `Ineligible` for `for await`, `using`, and an `await` inside a tree-walked node, and `host_async_function` runs the chunk to its first `await` on the Rust stack. A parked activation lives in `Interpreter::async_activations` (traced by `collect_async_activation_roots`) and resumes through `ReactionTarget::AsyncResume(id)` in `async_function_resume`, so PromiseResolve and tick counts are the state machine's. Async generators whose body the compiler can host are `IteratorState::BytecodeGenerator` with `is_async` (`eval/async_gen_chunk.rs`, ADR-2026-10-19-2310): `yield e` compiles to `e; await; yield` and its return stub starts with an `await`, `return e` awaits `e`; the scheduler's request queue is unchanged and `async_gen_drain` serves it. A state-machine driver step pins its innermost lowered scope on `call_stack_envs` (`pin_driver_env`): scopes entered during a run reach the scheduler's saved state only at the next suspension.
- Generators that stay on the state machine are compiled by `generator_transform.rs` into a `GeneratorStateMachine` (`generator_runtime.rs`): each resume jumps straight to the stored state id and suspends via `StateTerminator::Yield`/`Await`, with no replay. A `self.generator_context`/`SentValueBindingKind::InlineYield` fallback still exists in `generator_runtime.rs` for any construct the transform's analysis doesn't (yet) decompose — it re-executes the current state's statement list and fast-forwards past already-fired yields — but it is a degraded-behavior backstop for undiscovered gaps, not the primary mechanism (see issue #625). In async generators an inline `yield`/`yield*` suspends through the same terminator machinery as a lowered one (no blocking `await_value`, see ADR-2026-09-21-2157); only the replay of the state's preceding statements remains.
- The generator/async lowering emits three AST forms the parser never produces, so that evaluation order matches the spec across a suspension without observable lookups: `Expression::BoundCallee(func, this)` (a call or tagged-template callee whose function was already read into a temp; `eval_call`, the tagged-template arm and the bytecode `compile_call` resolve it without a property read), `Expression::PreIterated(array)` under a `Spread` (a fresh array built by one earlier iteration, spread by copying its elements through `spread_values` instead of iterating it again), and `FunctionDecl.phase` (`DeclPhase::InstantiateOnly` at the head of a block's first state creates the function and skips the Annex B.3.3 var copy; `CopyOnly` stays where the declaration is reached, is skipped by `hoist_function_decl`, and performs the copy). `compile_expr` treats the first two as non-standalone, so a parent that cannot lower them natively falls back as a whole.
- Closures of one function literal share an `Rc<FunctionLiteralInfo>` (parameter patterns, `uses_arguments`, `has_simple_params`) held in the AST node's `LiteralInfoCell`, alongside the per-`Body` `BodyMemo`s (#900). The cell is filled on first closure creation and `Clone` yields an empty cell, so a cloned-then-mutated node never carries a stale value; a path that clones the node per evaluation (e.g. the per-step `StateTerminator` clone in generator/async state machines) only loses sharing, never correctness.
- Named property access in the bytecode VM (`GetProp`/`LoadMethod`/`SetProp`/`UpdateProp`, `get_prop_op` & co. in `vm.rs`, #1029): `Interpreter::named_get_fast`/`named_store_fast`/`named_update_fast` (`property.rs`) complete a data-property access in place, bypassing the generic [[Get]]/[[Set]] chain, when the receiver and every prototype up to the holder are ordinary. `ObjectKind::is_named_access_exotic` (an exhaustive `match`: classify every new kind there) plus `named_miss_is_ordinary` (String wrappers) decide what is ordinary; Array `length`, Array-index-like names, accessors on a store, non-writable properties and non-extensible receivers fall back (`own_named_record_mut`). An add runs only when the prototype chain does not mention the name and must bump `shape_id` (`add_named_fast`); a store that lands runs `gc_write_barrier_value`. A getter found on the chain is returned (`NamedGet::Getter`) and called with the original receiver, so the generic path never re-walks. The four ops stay out of line: inlining them into `run_chunk_inner` changed the dispatch loop's code generation and cost 2-4% on workloads that never touch a named property.
- A literal's `LiteralFrame` also caches the interned own-name atom of a named function expression or hoisted function declaration (`own_name_atom`: the closure's name binding is pushed with no hashing) and the `name` string value (`name_string`, re-checked against the name because the default class constructors share one frame across names), so neither is built per closure. A shared immutable own-property prefix for closures was tried and dropped: any extra arm or check in `PropertyMap::slot_of`/`entry_at` made LLVM stop inlining the hinted lookup and cost 2-4% Ir on property-heavy benchmarks (`docs/perf/2026-10-19/1028-closure-construction.md`).
- Function objects are built by `create_function_with` from pre-interned `FunctionKeys` via `JsObjectData::push_fresh_property` (no per-closure key hashing; `tests/perf_counters_function_creation.rs` gates `key_intern_calls`). `PropertyMap` stays a linear scan up to `LINEAR_MAX = 8` entries before hashing. `JsObjectData.function_realm()` replaces the old function-to-realm map; `None` keeps the caller's realm. `class_name` is a `&'static str`: assign a literal for static tags (the native error constructors map their name to one).
- `new.target` is the `[[NewTarget]]` of the function environment, stored beside `this` in `ThisBinding.new_target` and resolved by the same chain walk (`Environment::get_new_target`): arrows, direct eval, field initializers (undefined) and resumed async/generator bodies need no capture or save/restore. `Interpreter::new_target` is only the hand-off to a *native* constructor (`apply_new_target_prototype`, `get_prototype_from_new_target_realm`), set by `call_constructor_body` and cleared while a user body runs.
