# Library Tests: TypeScript `conformance` runner, directory `types` (#1274)

Split from [library-tests-typescript.md](library-tests-typescript.md) to keep each file under the 20,000-byte budget; the machinery is the `compiler` runner oracle's ([library-tests-typescript-compiler.md](library-tests-typescript-compiler.md)).

**What it is.** `TS_SRC_DIR=<built TypeScript v6.0.3 checkout> uv run python scripts/run-ts-conformance-types-oracle.py [oracle options] [slice ...]` runs `tests/cases/conformance/types` (857 suites, 5142 tests: the `types` bucket of the `conformance` runner in `ts-suite/oracle.json`) through mocha and `built/local/run.js` on Node and `jsse --node` and compares them test by test. The `conformance` runner is a second `CompilerBaselineRunner`: one suite per test file (or per `// @target` configuration of it), titled `conformance tests conformance tests for tests/cases/conformance/<dir>/<file>`, with the compiler runner's six tests (errors, module resolution tracing, sourcemap content, JS output, sourcemap output, type/symbol baselines), baselines in `tests/baselines/reference` and mismatches written under `tests/baselines/local`.

**Wiring.** `scripts/run-ts-compiler-oracle.py` only knows the `compiler` runner, so the wrapper loads it as a module and replaces its runner settings (mocha `test.config` runner, suite grep, slice module, pinned-count lookup) instead of editing it. The slice module `scripts/ts_conformance_slices_1274.py` has the compiler slices' API with conformance titles, the term `dir:types/union`, and rows for `types` (the default) and its thirty subdirectories. Options, the baseline-file comparison, the corrupted-reference control (up to seven suites) and the known-failure ratchet are the compiler oracle's; the known failures live in `ts-suite/conformance-types-known-failures.txt` (`full test title<TAB>issue`, `--record` rewrites it). `--jobs` is capped at 4 and `--require` makes a missing checkout an error. Guards: `scripts/test_ts_conformance_types_1274.py` (slice selection, title parsing, grep, pinned count, wrapper settings), `tests/node_ts_conformance_types.rs` (Node-only listing: 857 suites, 5142 tests, subdirectory rows add up; needs `TS_SRC_DIR`).

**Cost.** A jsse process takes about 80 s to load the 13 MB runner bundle plus 25 to 75 s for the first `Program`, so suites run in batches of 40 (one process per engine and batch, at most 4 processes at once). The default run is 22 batches per engine.

**Measured** (jsse built from 22c4756b with `CARGO_PROFILE_RELEASE_LTO=off`, `--jobs 4`, 22 batches of 40 suites, a shared 24-core host): Node 5142/5142 passing in 64 s of process time, jsse 5142/5142 passing in 3170 s of process time, about 15 minutes of wall time including the control (batch times 150 s to 670 s). Per-test outcomes agree, no `tests/baselines/local` file is written by either engine, and the seven-suite corrupted-reference control (appended-to, rewritten, removed and added references) fails the same seven tests with the same messages and local baselines on both. The known-failure list `ts-suite/conformance-types-known-failures.txt` is empty and no engine or host change was needed. The earlier run with the compiler oracle's 600 s limits (5136 of 5142 on jsse, 7364 s of process time on a host at load average 40) failed on one suite only: the `before` hook of `types/literal/templateLiteralTypes1.ts` timed out, because that file type-checks in about 470 s on jsse (3 s on Node) and the limit fell inside the loaded run; alone it passes on both engines. The wrapper therefore defaults to `--test-timeout 1800000` and `--timeout 7200`. That is a speed gap of the interpreter on a compute-heavy type check, not a behaviour difference.
