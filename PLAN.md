# Plan: Implement `Iterator.prototype.chunks` and `Iterator.prototype.windows` (#548)

## 1. Problem restated

`Iterator.prototype.chunks` and `Iterator.prototype.windows` are missing from jsse's `Iterator.prototype` entirely (`typeof Iterator.prototype.chunks === "undefined"`), so all 138 test262 scenarios that exercise them fail after the test262 bump to `7710052` (#547). Both are lazy iterator-helper methods from the `iterator-chunking` TC39 proposal: `chunks(chunkSize)` partitions an iterator into fixed-size, non-overlapping arrays (last one short if the length isn't a multiple of `chunkSize`), and `windows(windowSize[, undersized])` produces overlapping sliding-window arrays, with `undersized` controlling whether a short trailing window is emitted (`"allow-partial"`) or dropped (`"only-full"`, the default). Both must integrate with the existing `%IteratorHelperPrototype%` machinery (lazy, single-pass, closeable, re-entrancy-guarded) the same way `map`/`filter`/`take`/`drop`/`flatMap` already do.

## 2. Spec basis

`sec-iterator.prototype.chunks` and `sec-iterator.prototype.windows` do **not** exist in `spec/spec.html` — the `iterator-chunking` proposal is not yet merged into ecma262. There is therefore no `spec/` clause to cite for the two new methods' own algorithm steps. Per test262 contribution convention, every test file's `info:` frontmatter transcribes the exact proposal algorithm text under the `esid` it tests (`sec-iterator.prototype.chunks` / `sec-iterator.prototype.windows`); this is the only written spec text available. Cross-checking ~30 files per method in `test262/test/built-ins/Iterator/prototype/{chunks,windows}/*.js` gives a consistent, non-contradictory algorithm (the step *numbers* differ slightly file to file — e.g. `argument-effect-order.js` numbers `GetIteratorDirect` as step 7, `get-next-method-only-once.js` calls it step 5 — because each file's `info:` is a step-numbered excerpt of the same underlying algorithm at different points of proposal-text revision; the step *ordering relations* below are consistent across every file and are what this plan relies on, not any single file's numbering):

**`Iterator.prototype.chunks(chunkSize)`**
1. `O` = this value; if not an Object → **TypeError**.
2. If `chunkSize` is not a Number (no `ToNumber` coercion — `chunkSize-no-coercion.js` asserts `valueOf`/`toString` are never called) → **TypeError**, then `IteratorClose(O, error)` (discarding any error the close itself produces — `argument-validation-failure-close-throws.js`).
3. If `chunkSize` is not an integral Number (`NaN`, non-integer, `±Infinity`) → **TypeError** (`chunkSize-not-a-number.js`), same close-and-discard.
4. If `chunkSize` is not in `[1, 2^32 - 1]` → **RangeError** (`chunkSize-out-of-range.js`), same close-and-discard.
5. `iterated` = `GetIteratorDirect(O)` (reads `.next` exactly once — `get-next-method-only-once.js`; only reached after all validation passes — `argument-effect-order.js` shows the `next` getter is *not* invoked when validation fails first).
6. Return a new `%IteratorHelperPrototype%`-based iterator whose closure repeats: pull one value via `IteratorStepValue`; on `~done~`, yield the buffered-so-far array if non-empty, then finish (no further `IteratorClose` of the underlying iterator — `exhaustion-does-not-call-return.js`); otherwise append to `buffer`, and once `buffer` reaches `chunkSize` elements, yield `CreateArrayFromList(buffer)` and reset `buffer` to empty (`chunks-evenly-divisible.js`, `chunks-last-chunk-partial.js`, `chunks-size-1.js`, `chunks-size-larger-than-iterator.js`).

**`Iterator.prototype.windows(windowSize[, undersized])`**
Same `O`/`windowSize` validation as `chunks` (Number-typed, integral, `[1, 2^32-1]`, TypeError/TypeError/RangeError in that order), **then**, still before `GetIteratorDirect`: if `undersized` is `undefined`, default to `"only-full"`; if it is neither the exact string `"only-full"` nor `"allow-partial"` → **TypeError** (`undersized-invalid.js` — no coercion: `0`, `true`, `{}`, `''`, `Symbol()` all throw), same close-and-discard. Then `GetIteratorDirect`. The closure: pull one value; on `~done~`, if `undersized` is `"allow-partial"` and `buffer` is non-empty and shorter than `windowSize`, yield it once, then finish either way (`iterator-already-exhausted.js`, `windows-allow-partial.js`); otherwise, if `buffer` already has `windowSize` elements, drop its first element, append the new value, and if `buffer` now has `windowSize` elements, yield `CreateArrayFromList(buffer)` **without clearing it** (sliding window — `windows-basic.js`: 5 elements, `windowSize` 2 → 4 windows `[0,1] [1,2] [2,3] [3,4]`, not 5, because after the first full window the buffer never drops below `windowSize` again so the tail condition never re-fires).

Both methods reuse already-merged ecma262 abstract operations that jsse already implements for `map`/`filter`/`take`/`drop`/`flatMap`:
- `GetIteratorDirect` — `spec/spec.html`, `emu-clause id="sec-getiteratordirect"`.
- `IteratorStepValue` — `spec/spec.html`, `emu-clause id="sec-iteratorstepvalue"`.
- `IteratorClose` — `spec/spec.html`, `emu-clause id="sec-iteratorclose"`.
- `CreateArrayFromList` — `spec/spec.html`, `emu-clause id="sec-createarrayfromlist"`.
- `%IteratorHelperPrototype%` (`.next`/`.return`, generator-brand re-entrancy check) — `spec/spec.html`, `<h1>The %IteratorHelperPrototype% Object</h1>` (`throws-typeerror-when-generator-is-running.js` for both methods exercises this).
- `CreateIteratorFromClosure` — `spec/spec.html`, `emu-clause id="sec-createiteratorfromclosure"` (jsse's existing `create_iterator_helper_object` + native `next`/`return` closures is its established, already-shipped reimplementation of this AO — see §3).

No new JavaScript syntax is introduced. No new `ObjectKind` variant is needed (see §3/§6).

## 3. Files to touch

- `src/interpreter/builtins/iterators.rs` — add `chunks` and `windows` as two new `self.define_method(iter_proto_id, ...)` blocks, inserted after the existing `drop` block (~line 2159) and before `flatMap` (~line 2333), following the exact closure-state pattern already used by `take`/`drop`/`flatMap`: validate → `get_iterator_direct_getter` → `Rc<RefCell<state>>` → native `next`/`return` `JsFunction`s → `create_iterator_helper_object` → `set_helper_gc_roots`.
- `README.md` — update the pass count/percentage on line 9 (and any other pass-rate mentions) after the final test262 run, per repo rule 5. **Not part of the TDD slices**; last step before opening the PR.
- No parser/lexer/AST changes — these are ordinary method calls, not new syntax.
- No `docs/adr/` entry — this is a straightforward addition of two built-in methods using an established, already-shipped implementation pattern (`create_iterator_helper_object`/closure-based helpers); it is not a new architectural mechanism.

### Shared-seam decision

`chunks` and `windows` will be **two separate closure blocks**, not a single parameterized builder, matching this file's existing convention (`map`/`filter`/`take`/`drop`/`flatMap` are five independent blocks despite sharing the same this-check → arg-validate → `GetIteratorDirect` → state → `next`/`return` → `create_iterator_helper_object` skeleton). Sharing would require threading a buffer-discipline mode (clear-after-full vs. shift-and-slide) and an extra `undersized` parameter that only one of the two methods has through a common builder, for a skeleton that's already only ~15 lines of the ~150-line block. Two copies keep each method's control flow linear and independently readable, at the cost of some duplicated boilerplate — consistent with "many small changes beat one large change" and the file's own precedent.

### Buffer representation (GC-rooting decision)

The `buffer` in both algorithms must be a **real jsse `Array` object** (`self.create_array(vec![])`), created once when the helper is constructed and included in the single `set_helper_gc_roots` call alongside `iter`/`next_method` — not a bare `Rc<RefCell<Vec<JsValue>>>` living only inside the closure. Two reasons:
- **Correctness.** `pin_native_root`'s own doc comment (`src/interpreter/gc.rs:174-193`) states a `JsValue` captured only inside a native closure's `Rc<dyn Fn>` is invisible to `trace_object_fields` and free to be collected between calls unless pinned on a traced anchor. A plain `Vec<JsValue>` buffer living in the closure's `RefCell` state has exactly this problem: values can sit in the buffer across multiple `.next()` calls on the *outer* iterator, and arbitrary JS (hence GC) can run between those calls.
- **No leak, no OOM.** `ObjectKind::Array` elements are already traced generically via jsse's normal property walk (`gc.rs:977-980`, "Array elements are visited via the property walk above"), so mutating the buffer array in place with `array_elements_mut()` (same low-level entry point `Array.prototype.push`-style code already uses, e.g. `array.rs:705`) keeps every buffered value alive with **zero additional per-element rooting calls** — unlike repeatedly calling `pin_native_root` per pushed value, which never un-pins (`gc.rs:191-192`) and would leak one root per element ever produced for the helper's whole lifetime. It also avoids ever calling `Vec::with_capacity(chunkSize)` with an attacker-controlled `chunkSize` up to `2^32 - 1` (`chunkSize-out-of-range.js`'s boundary case constructs `chunks(2**32 - 1)` without OOM-ing).

Each yielded chunk/window is then a **fresh, distinct** array built via `self.create_array(buffer_snapshot)` (satisfying `yields-distinct-arrays.js` for both methods), leaving the persistent buffer array to keep accumulating or sliding.

**Related finding, out of scope for this PR:** while confirming this design against `flatMap`'s existing implementation (`iterators.rs:2382-2513`), the `inner_iter`/`inner_next` fields it dynamically reassigns mid-iteration (`iterators.rs:2469-2470`, `state_next.borrow_mut().4 = Some(new_inner)`) are **never** passed to `pin_native_root` after the initial `set_helper_gc_roots` call (which only sees them while still `None`, at construction time — `iterators.rs:2554-2559`). That looks like the same latent GC-rooting gap this plan is designing around, pre-existing and unrelated to #548. Filed as [issue #556](https://github.com/pmatos/jsse/issues/556) (not fixing it here — out of scope, see §7).

**Gap not covered by test262** (test262 has no GC hooks): whether buffered-but-not-yet-yielded values in `chunks`/`windows` survive a GC cycle that runs *between* two `.next()` calls on the helper, while the partially-filled buffer holds the only live reference to some of its elements. Add `test262-extra/iterator-chunks-windows-buffer-gc-rooting.js`, modeled on the existing `test262-extra/Array-literal-spread-gc-rooting.js` pattern (`$262.gc()` forced mid-sequence): build a `chunks(3)`/`windows(3)` helper over a generator that yields freshly-allocated objects, call `.next()` once (buffer now holds 1-2 objects, chunk/window not yet complete), call `$262.gc()`, then finish filling the buffer and assert the earlier buffered object(s) are still the same reference (not corrupted/replaced) when the completed array is yielded. `esid: sec-iterator.prototype.chunks` / `sec-iterator.prototype.windows`, `features: [iterator-chunking]`.

## 6. Regression risk

- **`gc_safepoint()` / tracer**: the whole point of §3's buffer design is to keep this from becoming a rooting gap. The `test262-extra` addition in §5 is the regression guard for it.
- **`ObjectKind` exhaustive match**: no new variant added (helper reuses `ObjectKind::IterHelper` and `ObjectKind::Array`, both already handled in `gc::trace_object_fields`), so no compile-time-forced match update.
- **`Iterator.prototype` shape**: two new own, non-enumerable, writable, configurable data properties (`chunks`, `windows`). Grep before merging for anything asserting an exact `Object.getOwnPropertyNames(Iterator.prototype)` count/list — none found in `src/` or `scripts/` during planning, but the library-harness bundles (`scripts/run-library-tests.sh`) or `tests/` could conceivably enumerate iterator-helper method names; a full `cargo test --bin jsse` plus the standard library-test suite (already run in CI, not re-run here per plan scope) is the backstop.
- **`define_method`/fmt-clippy hook**: per memory, editing `iterators.rs` triggers a PostToolUse rustfmt+clippy(-D warnings) gate; keep the two new closures warning-clean the way `take`/`drop`/`flatMap` already are (in particular `#[allow(clippy::type_complexity)]` on the state tuple type, matching existing precedent in this file).
- **Tree-walker hot path (`eval_expr`/`exec_statement`)**: untouched — these are native-function closures reached through ordinary method-call dispatch, no interpreter core changes.
- **Bytecode fast path**: untouched — native builtins are called the same way from both the tree-walker and the VM; no new AST shape is introduced.
- **`test262-pass.txt` baseline**: this PR only adds previously-failing tests to the passing set; it cannot regress anything already passing, and per constraints the baseline file itself is not touched (`--update-baseline` is a `main`-branch operation, not part of this plan).

## 7. Out of scope

- Fixing the `flatMap` GC-rooting gap found during design research (§3) — tracked as [issue #556](https://github.com/pmatos/jsse/issues/556); do not bundle a fix into this PR.
- Any refactor of `map`/`filter`/`take`/`drop`/`flatMap` to share a common builder with the new methods (see §3's shared-seam decision) — the two new methods are additive only.
- `AsyncIterator.prototype.chunks`/`.windows` — test262 has no `AsyncIterator` counterpart tests (`test262/test/built-ins/AsyncIterator/` has no `chunks`/`windows` directories), so the proposal's synchronous surface only is in scope here.
- Rolling `test262-pass.txt` forward (`--update-baseline`) — a `main`-branch operation, not performed on this feature branch.
- Any bytecode-VM-specific fast path for the new methods — they go through the same native-builtin dispatch as every other iterator helper; no bytecode work is implied or planned.
