# Plan: issue #738 — nested block-scoped `let`/`const` in a generator loses TDZ across a suspension point

## 1. Problem restated

When a generator (or, as this plan shows, a plain async function or async generator) contains a nested block that both (a) declares a `let`/`const`/`class` name shadowing an outer `var`/parameter of the same name, and (b) contains a suspension point (`yield`, `yield*`, or `await`) anywhere in the block, jsse's generator-state-machine lowering splits that block's statements across multiple `GeneratorState`s. Each split fragment only pre-declares (as TDZ) the lexical names that appear *textually within that one fragment*, instead of the block's full set of lexical names up front. A read that happens in an earlier fragment — before the fragment containing the shadowing declaration has run — finds no binding for the name in the block's own `Environment` and falls through the environment parent chain to the outer `var`/parameter, instead of hitting TDZ and throwing. Without a suspension point in the block, the block is never split (it runs as one ordinary `Statement::Block`), so the existing single-shot hoist already declares every name up front and the bug does not manifest — exactly matching the issue's report. The identical defect also affects a generator/async `catch` clause's own block body, via a structurally different (but analogous) mechanism (`StateTerminator::EnterCatch`, see §3).

## 2. Spec basis

- `sec-block-runtime-semantics-evaluation` (Block Runtime Semantics: Evaluation) — entering a `{ StatementList }` creates one new Declarative Environment Record (`NewDeclarativeEnvironment`) and performs `BlockDeclarationInstantiation` against it **before** any statement of the block is evaluated.
- `sec-blockdeclarationinstantiation` (BlockDeclarationInstantiation) — for **every** element of the block's `LexicallyScopedDeclarations` (computed once, over the whole block), creates an uninitialized (`CreateMutableBinding`/`CreateImmutableBinding`) binding in that one Environment Record. This is the step jsse's generator lowering currently performs per split-fragment instead of once per block, which is the root cause.
- `sec-static-semantics-lexicallyscopeddeclarations` (Static Semantics: LexicallyScopedDeclarations) — defines that a block's own lexical declarations are exactly its *directly nested* `let`/`const`/`class`/function declarations (not those of nested blocks, loops, or function bodies) — i.e. a shallow, non-recursive scan. jsse's existing `hoist_lexical_declarations` (`src/interpreter/exec.rs:570`) already implements this shallow scan correctly; the bug is only about *when* (per-fragment vs. per-block) it runs for generator/async-function state machines.
- `sec-declarative-environment-records-getbindingvalue-n-s` (Declarative Environment Record `GetBindingValue`) — "If the binding exists but is uninitialized, throw a ReferenceError, regardless of ... `S`" — this is TDZ. jsse's `Environment::get` (`src/interpreter/types.rs:1186`) already implements this correctly (returns `None` for an uninitialized binding without falling through to the parent) — the bug is that the binding doesn't *exist yet* in the block's Environment when the read happens, so the normal parent-chain fallthrough (correct behavior for a genuinely undeclared name) fires instead of the TDZ path.
- `sec-runtime-semantics-catchclauseevaluation` (Runtime Semantics: CatchClauseEvaluation) — creates one Environment Record for the `CatchParameter`, then evaluates the catch `Block`, which (per `sec-block-runtime-semantics-evaluation` above) creates its *own*, second, nested Environment Record for the block's own declarations. jsse's tree-walker (`exec.rs:2504-2517`, `catch_env` then a distinct child `catch_block_env`) implements this correctly; the generator/async-function state-machine drivers' `EnterCatch` handling does not create that second environment at all (see §3, §7) — a pre-existing, narrower gap than this issue, but the reason the catch-body fix below only pre-declares into the single existing environment rather than adding the missing layer.

No new JavaScript syntax or semantics are introduced. This is a pure conformance fix: jsse's internal generator/async-function state-machine lowering must preserve `BlockDeclarationInstantiation`'s atomicity across suspension-point splitting, exactly as an ordinary (non-generator) block already does.

## 3. Files to touch

### 3a. Plain blocks, loop bodies, try-bodies, finally-bodies, for-head (the `ScopeAction::OpenBlock` sites)

- `src/interpreter/generator_transform.rs`
  - `ScopeAction::OpenBlock` (~line 52): change from a unit variant to carry the block's own lexical declarations, `Vec<(String, bool)>` (name, `is_const`) — the same shape `ScopeAction::CopyForward` already uses, for a reason (see Regression risk).
  - Add a small free function (name suggestion: `collect_block_lexical_decls(stmts: &[Statement]) -> Vec<(String, bool)>`) placed near the other block-transform helpers. It performs the exact same shallow scan as `hoist_lexical_declarations` (`Statement::Variable` with `VarKind::Let|Const|Using|AwaitUsing` → collect `bound_names`; `Statement::ClassDeclaration` with a name → the class name), over the **whole**, unsplit block statement list — not a fragment.
  - Update all four `ScopeAction::OpenBlock` construction sites to pass the block's own list:
    - Line ~979 (`transform_yielding_statement`'s `Statement::Block` arm — plain blocks, loop bodies): `collect_block_lexical_decls(stmts)`, where `stmts` is the full block passed into that match arm (already unsplit at that point).
    - Line ~3052 (`transform_try_statement`, try-body): `collect_block_lexical_decls(&try_stmt.block)`.
    - Line ~3106 (`transform_try_statement`, finally-body): `collect_block_lexical_decls(finalizer)`.
    - Line ~2669 (`transform_for_statement`, for-head per-iteration frame): reuse the `per_iteration_bindings` list already computed a few lines earlier (~2642) for the sibling `ScopeAction::CopyForward` calls at the same site — it is already exactly the right `Vec<(String, bool)>` shape for the head's own `let`/`const` names, just not yet threaded through `OpenBlock`.
- `src/interpreter/exec.rs`
  - `reconcile_scope_stack`'s `OpenBlock` arm (~line 2011-2018): after `Environment::new(Some(parent))`, declare every `(name, is_const)` pair into the fresh Environment via `.declare(name, kind)` (kind = `BindingKind::Const` if `is_const` else `BindingKind::Let`) — **do not** call `initialize_binding`; the binding must stay in TDZ until the state whose body contains the actual declaration statement executes and initializes it, exactly as today. This mirrors, but does not initialize like, the existing `CopyForward` arm just below it (~2019-2045).

### 3b. Catch-clause bodies (the `StateTerminator::EnterCatch` sites)

A catch clause's body is textually a nested `Block` too (grammar: `Catch : catch ( CatchParameter ) Block`), and suffers the identical timing defect through a different mechanism: `catch_body_state` never gets an `OpenBlock` scope action (it reuses the single environment `EnterCatch` creates for the parameter — see §2/§7), so its own lexical names are only ever declared per-fragment, exactly like the pre-fix `OpenBlock` case.

- `src/interpreter/generator_transform.rs`
  - `StateTerminator::EnterCatch` (~line 142-145): add a field, e.g. `lexical_decls: Vec<(String, bool)>`.
  - At its one construction site in `transform_try_statement` (~line 3064-3067), populate it with `try_stmt.handler.as_ref().map(|h| collect_block_lexical_decls(&h.body)).unwrap_or_default()`.
  - `clear_terminator_ic_sites`'s `EnterCatch` arm (~line 287-291) needs no change (the new field holds no expressions), but confirm the match still compiles (`{ param, .. }` already ignores other fields).
- `src/interpreter/eval/generator_runtime.rs` (sync-generator driver, ~line 1565-1583; async-generator driver, ~line 4747-4765) and `src/interpreter/eval.rs` (plain async-function driver, ~line 9142-9162): in each `StateTerminator::EnterCatch` handler, immediately after binding the param into `catch_env` and before pushing the `ScopeFrame`, declare every `(name, is_const)` pair from the new field into `catch_env` the same way as §3a (TDZ, not initialized).

## 6. Regression risk

- **`ScopeAction::OpenBlock` and `StateTerminator::EnterCatch` shape changes are breaking changes to every construction/consumption site** — the compiler enforces every site is updated; no site can be silently missed the way a runtime-only regression could be. (This is exactly how the original draft of this plan almost missed the catch-body site: it compiles fine either way, since `EnterCatch` is a separate terminator from `OpenBlock` — there is no compiler forcing function linking the two. Both sites were verified by direct code reading, not inferred from the enum change alone.)
- **`Environment::declare` unconditionally resets a binding to uninitialized** (`src/interpreter/types.rs:1029`, unconditional `self.bindings.insert(...)`). After this fix, a later-executing state's own `hoist_lexical_declarations` call (`exec.rs:267`, unchanged) will *redundantly* re-declare names that the new eager pre-declaration already declared. This is harmless **only** because a name's actual declaring statement is never split across two different generator states in the scenarios this fix touches — it either sits entirely within one fragment (ordinary case) or its own suspending initializer is lowered through the separate `SentValueBinding`/pattern-lowering path fixed by #722 (which re-synthesizes a normal `Statement::Variable` in one fragment). The positive-path assertions in every new test file (§4 slice 1) exist specifically to catch a violation of this invariant — if one of them starts failing after the fix (an already-initialized binding reset to TDZ on redundant re-declare), that is a real bug to fix as part of this same PR, not a pre-existing quirk to shrug off.
- **Loop-body per-iteration environments**: `ScopeAction::OpenBlock` is also used for loop bodies (per its own doc comment). This fix only adds data to the *push* path (`scope_stack.len() < target_depth`, i.e. genuine fresh-frame creation); it does not change *when* a fresh frame is created. Run the existing `for`/`while`/`do-while` generator test262 tests as part of the full-suite pass to catch any interaction.
- **`GeneratorAnalysis.local_vars`** (`src/interpreter/generator_analysis.rs:25`) looks like a tempting existing source of per-block lexical names, but was deliberately **not** reused: it is flat by `scope_depth` number only, with no per-block identity, so two sibling blocks at the same nesting depth would have their declarations conflated; it is also effectively dead code today (`TransformContext.analysis` is stored but never read anywhere in `generator_transform.rs` — confirmed by grep). The new `collect_block_lexical_decls` helper scans the exact `&[Statement]` slice of the one block in question, avoiding this trap entirely.
- **Shared blast radius**: the `OpenBlock` consumption site (`reconcile_scope_stack` in `exec.rs`) and the `EnterCatch` handling are each duplicated across all three state-machine drivers — sync generators, async generators, and plain async functions — so this fix, and any regression it introduces, affects all three simultaneously. This is why §4 slice 1 includes async-function and async-generator coverage even though the issue only reports the generator case.
- Does not touch the tree-walker hot path for non-generator/non-async code, the property MOP (`property.rs`), GC rooting, `ObjectKind` matches, or the bytecode fast path — the generator/async-function state machine is a distinct execution mode from all of those.

## 7. Out of scope

- **Switch `CaseBlock` scoping in a split generator switch is a separate, larger bug, not fixed here.** Confirmed by reading `transform_switch_statement` (generator_transform.rs:3188+): it never bumps `scope_depth` and never sets any `scope_action` for its case states, while the ordinary tree-walker (`exec_switch`, `exec.rs:2548-2553`) always creates a `switch_env` for the whole `CaseBlock`. This means a generator `switch` whose cases contain a suspension point loses the `CaseBlock`'s environment **entirely** — not a TDZ-timing issue but a complete absence of case-level block scoping — which is a materially bigger bug than #738's timing defect. Worth its own issue.
- **`await using` blocks (`StateTerminator::EnterScope`/`ExitScope`, the narrow plain-async-function case) have the identical bare-`Environment::new`-with-no-pre-declare pattern** (`eval.rs:9619-9627`) as the pre-fix `OpenBlock` code. A `let`/`const` shadowing an outer binding inside a block that also declares `await using` and suspends would have the same TDZ-loss symptom. Not included in this PR to keep it reviewable (it is a third, structurally distinct mechanism beyond `OpenBlock` and `EnterCatch`, and gated behind a narrower, newer feature); worth a follow-up using the same `collect_block_lexical_decls` helper once this PR lands.
- **The catch clause's body environment stays merged with its parameter environment** in the generator/async-function state-machine drivers (spec wants two nested environments per §2's `CatchClauseEvaluation` + `Block` reading; jsse's tree-walker already gets this right, `exec.rs:2504-2511`). This PR's `EnterCatch` fix (§3b) declares the body's own lexical names into the *existing* merged environment, which correctly fixes the suspension-across-TDZ symptom for names that don't collide with the catch parameter's own name — but a catch body declaration that happens to share its name with the parameter (`catch (e) { let e = 1; ... }`) remains separately broken, with or without a suspension point, exactly as it was before this PR. That pre-existing, narrower collision bug is unrelated to suspension splitting and should be filed separately.
- **`for (let i = ...; ...)` head TDZ-among-sibling-declarators** (e.g. `for (let i = j, j = 1; ...)`, where evaluating `i`'s initializer should see `j` in TDZ): the for-head `OpenBlock` site (~line 2669) is updated in this PR only because the correct data (`per_iteration_bindings`) is already sitting right there for the sibling `CopyForward` calls — wiring it through costs nothing and can only help. No new test targets this specific multi-declarator-TDZ shape; if it turns out to still be broken, file it separately, since it is a different splitting mechanism (`transform_variable_declaration`, one `VariableDeclaration`'s own declarators) from the "arbitrary statement list split across states" mechanism this issue is about.
- **Block-scoped function declarations split across suspension points**: `hoist_function_decl` (`exec.rs:540`) is called per-fragment the same way `hoist_lexical_declarations` was, and could have an analogous "not yet instantiated in an earlier fragment" gap for `function` declarations directly inside a block. The issue as filed is specifically about `let`/`const` TDZ; block-scoped function declarations are initialized immediately (no TDZ) rather than throwing, so the user-visible failure mode would be different (wrong/missing function value, not a missed throw) and deserves its own investigation and issue rather than being folded into this fix.
- No refactor of `hoist_lexical_declarations` itself, no removal of the dead `GeneratorAnalysis`/`local_vars` code path (confirmed dead, but removing it is a separate cleanup, not this bug fix), no changes to the bytecode fast path, and no rewording of unrelated doc comments beyond the one `ScopeAction::OpenBlock` comment this fix's behavior change makes newly inaccurate (§3c).
- No baseline update (`test262-pass.txt` stays untouched by this PR; the implementation stage runs the full suite only to confirm no regression against `origin/main`'s baseline).
