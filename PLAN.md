# Plan: Tooling: add cargo-fuzz (parser + differential-vs-node targets)

Issue: #193
PR title (verbatim, for the squash-merge subject — lowercase, conventional-commit form):
`tooling: add cargo-fuzz parser and differential-vs-node targets`

## 1. Problem restated

`jsse` has no fuzz testing. test262 and the library harnesses are both corpus-based
regression suites — they only exercise inputs someone already wrote down. A
coverage-guided fuzzer can find parser panics and lexer/parser divergences from
`node` that no fixed corpus will ever produce, which directly serves the 100%
test262 goal per issue #192's DevX audit. Today this is impossible: the crate is
binary-only (`src/main.rs` with `mod ast; mod interpreter; ...`, no `src/lib.rs`),
so there is no library target for `cargo fuzz`'s libFuzzer harness to link
against. This plan (a) carves out a `[lib]` target with the parser/interpreter
reachable, (b) adds an in-process `parse_roundtrip`-named fuzz target (parse
must never panic/abort — no actual AST roundtrip printer exists, see §4 slice 5
naming note), (c) adds a subprocess-based `differential` target that runs the
same generated source through both the release `jsse` binary and `node` and
flags divergences in accept/reject and top-level error class, (d) commits a seed
corpus derived from `tests/` and `test262-extra/`, (e) wires a short-budget CI
smoke job plus an optional nightly deep-fuzz job, and (f) packages a
`.claude` skill so agents can drive fuzz runs and triage crashes without
re-deriving this design each time.

## 2. Spec basis

N/A: no JavaScript behavior change. This issue adds build tooling (`src/lib.rs`
re-exporting existing modules, unchanged), a `fuzz/` crate, CI jobs, and a
`.claude` skill. It changes nothing about what JavaScript source `jsse` accepts
or how it executes — the parser and interpreter modules move to a new crate
root unmodified. Any *bug* the fuzz targets surface (a parser panic, or a
divergence from `node`) is a **lead**, filed as its own follow-up issue and
fixed against the spec in its own PR — never "fixed" by matching `node`'s
observed behavior, and never fixed inside this PR (which only builds the
tooling). Bake this rule into the skill (§4 slice 8) so an agent triaging a
crash doesn't quietly bend the engine toward `node`.

## 3. Files to touch

**New:**
- `src/lib.rs` — new crate root exposing `pub mod ast; pub mod interpreter; pub mod lexer; pub mod parser; pub mod types;` (`emoji_strings`/`unicode_tables` stay `pub(crate)`, unused outside the crate) plus one reusable helper (see slice 2).
- `fuzz/Cargo.toml`, `fuzz/.gitignore` — generated by `cargo fuzz init`, detached `[workspace]` stub so it isn't pulled into the (nonexistent) root workspace. Depends on `jsse` via `path = ".."` and `libfuzzer-sys`.
- `fuzz/fuzz_targets/parse_roundtrip.rs` — in-process libFuzzer target, one-liner calling a testable lib fn.
- `fuzz/fuzz_targets/differential.rs` — subprocess-based target invoking `target/release/jsse -e` and `node -e`.
- `fuzz/corpus/parse_roundtrip/` — seed corpus copied/symlinked from `tests/*.js` and `test262-extra/*.js` (`.mjs` seeds excluded from this target for now; module parsing is a follow-up, see §7).
- `fuzz/corpus/differential/` — same seed set (shared script corpus; small subset chosen for subprocess-speed reasons, see slice 4).
- `.github/workflows/fuzz.yml` — new workflow (kept separate from `ci.yml`; see §6).
- `.claude/skills/fuzzing/SKILL.md` — new skill mirroring `performance-analyse`/`performance-fix`'s structure (read-only investigate step + a separate triage/fix step).
- `docs/adr/0003-fuzz-lib-target-and-subprocess-differential.md` — ADR recording two decisions that aren't obvious from the code: (a) why the differential target shells out to compiled binaries instead of linking the interpreter in-process, (b) why `parse_roundtrip` fuzzes bytes-in/no-panic rather than an actual print→reparse roundtrip.

**Modified:**
- `src/main.rs` — strip `mod ast; mod interpreter; mod lexer; mod parser; mod types;` and the two crate-level `#![allow(clippy::...)]` attributes (move to `lib.rs`); replace with `use jsse::{ast, interpreter, lexer, parser};` (exact set per what main.rs actually names) plus `use jsse::run_on_engine_stack;` for slice 2's extracted helper. No behavioral change — `cargo run` / the CLI must work identically.
- `Cargo.toml` — no changes expected (Cargo auto-detects `src/lib.rs` + `src/main.rs` as a lib + bin pair with the same defaults); confirm during implementation that an explicit `[lib]` section isn't needed for `cargo fuzz`'s generated dependency to resolve the crate name.
- `.cargo/mutants.toml` — add a comment noting `fuzz/` is a separate detached-workspace crate and is out of scope for `cargo-mutants` by construction (no `exclude_globs` entry needed since mutants runs against the root package only); add the entry only if implementation discovers otherwise.
- `scripts/lint.sh` — no change planned; `cargo fmt --check` / `cargo clippy -- -D warnings` at the repo root only cover the root package. Explicitly **not** extending lint.sh to cover `fuzz/` in this PR (see §7) — note this gap in the ADR instead of silently leaving it undocumented.
- `README.md` — add a short "Fuzzing" section (pointers to `fuzz/`, how to run locally, how CI runs it) alongside the existing test262 pass-count section. Not a pass-count change, so no baseline math involved.

## 4. TDD slices

Fuzz harnesses are `#![no_main]` and not directly unit-testable, so each slice puts
real logic in a testable library function first and makes the actual
`fuzz_targets/*.rs` file a thin, untested one-line call site — mirroring how
`scripts/run-test262.py` has `test_run_test262.py` next to it.

1. **Extract the lib target, prove parity, no behavior change.**
   - Test: `cargo test --release` (existing suite, now split across `--lib` and `--bin jsse` targets) plus a manual `cargo run --release -- -e "1+1"` smoke check.
   - Production: create `src/lib.rs` with `pub mod ast; pub mod interpreter; pub mod lexer; pub mod parser; pub mod types; pub(crate) mod emoji_strings; pub(crate) mod unicode_tables;` and the two `#![allow(clippy::...)]` attributes; strip the corresponding `mod` lines and attributes from `src/main.rs`, replacing with `use jsse::...`.
   - Gate: `./scripts/lint.sh` must stay clean on **both** targets (`cargo clippy --all-targets -- -D warnings` — the fmt-hook's per-edit gate already does this for `.rs` files; confirm the full-workspace run separately since `fuzz/` doesn't exist yet at this slice).
   - Verify no `pub(crate)`-only item that main.rs touches (`can_block`, `bytecode_enabled`, `pending_exit` on `Interpreter`) breaks compilation now that main.rs is a separate crate: widen exactly those three fields to `pub` (not `pub(crate)`) — grep-confirmed as the only three; `enable_node_host`, `run`, `new`, `format_value`, `Completion`, `ParseError` are already `pub fn`/`pub struct`/`pub enum` and need no change.

2. **Extract the big-stack thread spawn into the lib (blocker for slice 3).**
   - Why this is its own slice: `main()` currently runs all engine work on a hand-rolled 128 MiB thread specifically so `MAX_PARSE_DEPTH` (4000, `src/parser/mod.rs:81`) and `CALL_DEPTH_HARD_LIMIT` (5000) can throw their catchable `RangeError`/`ParseError` before the *real* OS stack (default ~8 MiB) overflows. A libFuzzer target's main thread does **not** get this treatment — feeding it `tests/recursion-limit-parser.js`-style deep nesting (which the seed corpus will include, and libFuzzer will happily deepen further) SIGABRTs on the default stack, which libFuzzer reports as a crash. That's noise, not a bug: the engine's own depth guard would have caught it correctly at 128 MiB.
   - Test (new, `src/interpreter/tests.rs` or a new `src/lib_tests.rs` under `#[cfg(test)]`): a helper run on the *default* test-thread stack — `run_on_engine_stack(|| jsse::parser::Parser::new(&"[".repeat(5000))?.parse_program())` — asserts `Err(ParseError)`, not a process abort. (This test only proves something if it's plausible to fail without the extraction — confirm by running it against a version that calls `Parser::new` directly with no big-stack thread first, expect SIGABRT/test-harness crash, then apply the fix.)
   - Production: extract `main()`'s stack-spawn-with-fallback logic (currently inline in `fn main`, `src/main.rs`) into `pub fn run_on_engine_stack<R: Send + 'static>(f: impl FnOnce() -> R + Send + 'static) -> R` in `src/lib.rs`, reusing the existing `ENGINE_STACK_SIZE` constant and the "spawn or fall back to current thread" logic verbatim. `main.rs`'s `fn main()` calls the new lib fn instead of duplicating the thread-spawn.

3. **`parse_roundtrip` fuzz target — parse must never panic/abort.**
   - Test: `cargo fuzz run parse_roundtrip -- -runs=0` (deterministic corpus replay, no new mutation) over the seed corpus from slice 4 must exit 0.
   - Production:
     - Testable lib fn (in `src/lib.rs` or a new `src/fuzz_support.rs` gated `#[cfg(any(test, fuzzing))]`... actually keep it simple and always-compiled, it's cheap): `pub fn fuzz_parse_bytes(data: &[u8])` — `let Ok(src) = std::str::from_utf8(data) else { return };` then `run_on_engine_stack(move || { let _ = jsse::parser::Parser::new(&src).and_then(|mut p| p.parse_program()); })`. Deliberately ignores the `Result` — a parse error is a normal outcome, not a finding; only a panic (caught by `libfuzzer-sys`'s panic hook, which still aborts the process on panic even inside the spawned thread — verify this at implementation time, since panics on a non-main thread must propagate) is.
     - Unit tests for `fuzz_parse_bytes` directly: empty input, invalid UTF-8 bytes, a valid small program, and the 5000-deep-bracket case from slice 2 — all must return normally.
     - `fuzz/fuzz_targets/parse_roundtrip.rs`: `#![no_main]` + `libfuzzer_sys::fuzz_target!(|data: &[u8]| { jsse::fuzz_parse_bytes(data); });`

4. **Seed corpus from `tests/` and `test262-extra/`.**
   - Test: `cargo fuzz run parse_roundtrip -- -runs=0 fuzz/corpus/parse_roundtrip` must accept every seed file without error (libFuzzer's own corpus-minimization pass, run once locally, not asserted in CI — CI only needs `-runs=0` to succeed).
   - Production: copy (not symlink — `cargo fuzz` corpus dirs are plain files and CI checkout needs them as real content) `tests/*.js` (skip `test262_smoke_oracle.rs`, the one non-JS file there) and `test262-extra/*.js` into `fuzz/corpus/parse_roundtrip/`; a curated subset (5–10 short, fast-parsing files, e.g. `tests/basic-expressions.js` and a couple of small `test262-extra/*.js`) into `fuzz/corpus/differential/` — kept small deliberately because slice 5's target pays a `node` process-spawn per run (see the ADR).

5. **`differential` fuzz target — jsse vs `node` on the same source, subprocess-based.**
   - Design constraint driving this: `grep`-confirmed there is no step/instruction budget in the interpreter (`step_budget`/`instruction_count`/interrupt search came back empty), so an in-process differential target fed `while(1){}` by the fuzzer would hang the whole libFuzzer process. Running `target/release/jsse -e <src>` as a subprocess — mirroring `scripts/run-test262.py`'s own per-test wall-clock timeout and memory limit — makes hangs a normal, cheap "kill and skip" outcome on *both* sides instead of a libFuzzer-level timeout/crash misclassification. This also sidesteps needing `CALL_DEPTH_*`/GC internals `pub`: the differential target never links the interpreter in-process at all.
   - Test: a unit test for the comparison function with canned `(jsse_result, node_result)` tuples — same-exit-class (both succeed, or both throw) is not a finding; jsse-crashes-where-node-doesn't is tier 1; a parse-accept/reject mismatch is tier 2; both-throw-different-error-class is recorded but explicitly **not** a fuzzer finding (see tiering below) so it doesn't drown the corpus in "feature not implemented yet" noise.
   - Production:
     - `pub fn run_engine_subprocess(jsse_bin: &Path, src: &str, timeout: Duration) -> EngineOutcome` and the analogous `run_node_subprocess` (both usable from `fuzz/fuzz_targets/differential.rs`; live in `fuzz/src/` since they're fuzz-crate-only, not part of the public `jsse` lib API). Each captures exit status, a timeout-vs-exit distinction, and (from stderr) a best-effort leading error-class token (`SyntaxError`/`ReferenceError`/`TypeError`/etc.) already produced by both engines' default error formatting.
     - Node side prepends `scripts/node-test262-prelude.js` (defines `print`) so seeds that call `print(...)` (grep-confirmed present in the existing corpus files) don't spuriously `ReferenceError` on node alone — that would be a false-positive divergence, not a real one.
     - Tiering, implemented as the fuzz target's only two `panic!()` call sites (libFuzzer's sole "this is a finding" signal):
       - **Tier 1 (panic):** jsse subprocess killed by a signal (SIGSEGV/SIGABRT/SIGILL) or exits with the interpreter-panic code (101) while node exits cleanly or with a normal thrown-error exit code. This is an engine bug by definition, independent of what node does.
       - **Tier 2 (panic):** one side reports a parse error and the other parses successfully (i.e. jsse's `SyntaxError:`-prefixed exit-2 path vs. node's parse outcome, or vice versa). Surfaces real syntax coverage gaps.
       - **Tier 3 (recorded, not a panic):** both sides throw, but the leading error-class token differs, or both time out. Too noisy to gate on (mostly "jsse hasn't implemented X yet"); the skill's triage step (§4 slice 8) is where a human/agent decides whether a specific Tier 3 sample is worth filing.
     - `fuzz/fuzz_targets/differential.rs`: locates the release `jsse` binary via `env!("CARGO_MANIFEST_DIR")` + `../target/release/jsse` (documented assumption: `cargo build --release` has already run — the CI job and skill both state this precondition explicitly), skips the whole run early (return, not panic) if either binary is missing so local `cargo fuzz run` without a release build doesn't false-positive.
   - State plainly in the ADR: this target's throughput is bounded by two process spawns per iteration (~tens of ms each) — realistically tens of iterations/sec, not the thousands/sec libFuzzer normally achieves. It is a nightly/`workflow_dispatch` target only, never the PR gate (see §6).

6. **CI smoke job.**
   - Test: the workflow itself, validated by `actionlint`/`zizmor` (already gated on every PR via `.github/workflows/workflow-lint.yml`) plus a real run once opened as a PR.
   - Production: `.github/workflows/fuzz.yml`, `pull_request`-triggered job `fuzz-smoke`:
     - `dtolnay/rust-toolchain@nightly` (cargo-fuzz requires nightly for sanitizer support — confirmed no `rust-toolchain.toml` currently pins nightly, so this job's toolchain choice is local to the job, not repo-wide).
     - Install `cargo-fuzz`: try `taiki-e/install-action@cargo-fuzz` first (same pattern as the existing `cargo-llvm-cov` install in `nightly-test262-coverage.yml`); fall back to `cargo install cargo-fuzz --locked` if it turns out not to be in taiki-e's supported-tool list — confirm which at implementation time.
     - `cargo build --release` (needed for the differential target's subprocess).
     - `cargo fuzz build parse_roundtrip` then `cargo fuzz run parse_roundtrip fuzz/corpus/parse_roundtrip -- -runs=0` (deterministic corpus-replay regression check — catches a parser panic on a *known* seed immediately, no new mutation, seconds not minutes) then a short bounded new-mutation pass `cargo fuzz run parse_roundtrip -- -max_total_time=60`.
     - `--sanitizer none` for this job: `unsafe` usage is small (29 hits, grep-confirmed) and ASan roughly doubles build time on top of an already `icu`-heavy dependency tree; record this trade-off in the ADR rather than silently picking it. (Nightly deep-fuzz job below can opt into the ASan default if desired — out of scope to decide now, listed in §7.)

     - `permissions: contents: read`, `persist-credentials: false` on checkout, pinned action versions — matching every existing workflow's pattern so `workflow-lint.yml` passes.
   - A second job (or a `schedule:`-triggered second workflow, decide during implementation which is more consistent with `nightly-test262-coverage.yml`'s existing pattern) runs `differential` with a longer `-max_total_time` on a `workflow_dispatch`/cron trigger — optional per the issue ("optional nightly deep-fuzz"), so keep it minimal: reuse the same install/build steps, just a longer time budget and the `differential` target added.

A Tier 3 "different error class" sample is either discarded (known unimplemented feature) or, if it looks like a genuine spec violation, promoted to a filed issue the same way.

## 5. Test surface

This is tooling, not an engine change, so the primary gates are the ones listed
per-slice above, not `test262/`:
- `cargo test --release` (and, once the lib exists, note whether `--lib` vs `--bin jsse` vs plain `cargo test` is the complete set — plain `cargo test` runs both targets and is the safest default going forward).
- `./scripts/lint.sh` (`cargo fmt --check` + `cargo clippy -- -D warnings`) on the root package after slice 1; a `fuzz/`-scoped `cd fuzz && cargo fmt --check && cargo clippy -- -D warnings` is **not** wired into `scripts/lint.sh` in this PR (see §7 Out of scope) but should be run manually once during implementation to confirm the generated fuzz targets are clean.
- `cargo fuzz run parse_roundtrip -- -runs=0` — deterministic corpus-replay regression gate, both locally during slices 3–4 and in CI (slice 6).
- `actionlint`/`zizmor` via the existing `workflow-lint.yml`, which already runs on every PR touching `.github/workflows/`.
- No `test262/` directory is relevant here — nothing under `language/`, `built-ins/`, `annexB/`, or `intl402/` exercises build tooling. If slice 5's differential target *finds* a real divergence during implementation, that finding is out of scope for this PR (filed as a follow-up issue per §2/§4-slice-8) and must not be special-cased into this PR's engine code.

## 6. Regression risk

- **`test262-pass.txt` baseline:** none of this plan changes engine behavior, so the baseline shouldn't move. The only way it could is if slice 1's mechanical `mod` → `pub mod` extraction accidentally changes something (e.g. a `cfg(test)` item's visibility altering which impl is picked, extremely unlikely here) — guarded by running the full existing `cargo test --release` and a spot-check `uv run python scripts/run-test262.py` subset (the same `test262/test/built-ins/Atomics/`-style smoke set `ci.yml` already runs) after slice 1, before proceeding to slice 2.
- **Shared machinery touched:** slice 1/2 touch crate-root module wiring and the `main()` thread-spawn — not the tree-walker hot paths, `property.rs` MOP, GC rooting, or the bytecode fast path themselves, only how the binary reaches them. The main risk is a visibility mistake (an item that needs to stay `pub(crate)` for a reason not caught by this plan's grep pass) causing a compile break, which `cargo build --release` in CI catches immediately, not silently.
- **CI cost/flakiness:** the new `fuzz-smoke` job adds a nightly-toolchain install + `cargo-fuzz` install + a from-scratch build to every PR's CI run (no `Swatinem/rust-cache@v2` reuse across the stable-vs-nightly toolchain boundary in `ci.yml`'s existing `build` job) — this is a real added wall-clock cost, mitigated by capping it to `-max_total_time=60` and giving it its own cache namespace. Flagged explicitly rather than glossed over.
- **`differential` target's subprocess model:** depends on both `target/release/jsse` and `node` existing on PATH/at a known location. If either is missing, the target must skip cleanly (return, not panic) — a missing `node` on a future CI image change must not turn into spurious "crashes." Local dev without a release build must degrade the same way.

## 7. Out of scope

- **Module-source (`.mjs`) fuzzing** — the seed corpus and `parse_roundtrip` target cover scripts only; module parsing (`parse_program_as_module`) is a natural follow-up target but adds import-resolution complexity (a fuzzed module can `import` an arbitrary nonexistent path) this PR doesn't need to solve.
- **A real AST-print → reparse roundtrip target** — would need an AST-to-source printer that doesn't exist yet (grep-confirmed no `Display for Program` / `to_source`). `parse_roundtrip` as scoped here is parse-must-not-panic only; renaming or building the true roundtrip is a follow-up once/if a source printer exists for other reasons.
- **Linking `fuzz/` into `scripts/lint.sh` / the root clippy gate** — deliberately left unwired; the fuzz crate's idioms (`#![no_main]`, `Arbitrary` derives) don't always play nicely with the same lint config as the main crate, and wiring it up carefully is its own piece of work.
- **In-process differential fuzzing with interpreter step budgets** — would let the differential target run at libFuzzer speed instead of subprocess speed, but requires adding an instruction/step budget to the interpreter (a real engine feature, with its own spec/perf implications) that doesn't exist today and is well beyond this issue's scope.
- **ASan/other sanitizers in the smoke job** — deferred per slice 6's `--sanitizer none` decision; revisit if the nightly deep-fuzz job wants stronger UB detection.
- **`cargo-mutants` awareness of `fuzz/`** — expected to be a non-issue by construction (separate detached workspace), but not verified end-to-end in this plan; if implementation finds otherwise, add the `exclude_globs` entry then, not speculatively now.
- **Any code fix for a bug the fuzzer actually finds during implementation** — filed as a follow-up issue per §2, never folded into this tooling PR.
